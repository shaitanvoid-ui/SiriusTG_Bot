# Этап 7: выдача подарков — 03.10.2026

Реализован обычный Stars-процесс через личный аккаунт владельца Telethon.
Bot API sendGift, resale, TON, аукционы и запасная сессия не используются.
Каталог учитывает цену, sold-out, Premium, per-user limits, locked gifts и
глобальную блокировку подарков в конфигурации Telegram. Карточки и действия
остаются нативными Telegram, тексты находятся в locales, числа — в settings.

## Учёт и данные

Внутренняя единица разделена на 10 000 целых долей. Существующее округление
начислений до сотых описано через Decimal HALF_EVEN. Ни курс, ни комиссия
не добавлены. Счёт пользователя, его резерв и настоящий Stars-баланс
отправителя разделены. Погашение долга сохраняется, возврат резерва сначала
погашает возникший долг. Подробнее: [EXACT_MONEY.md](EXACT_MONEY.md).

Миграция 0014 переводит все финансовые поля из Float в целые доли и создаёт
money_migration_audit и money_operations. Для каждого исходного поля записаны
исходная величина, целые доли и объяснимая разница округления; начальные записи
журнала устанавливают обязательства без повторного начисления наград.
0015 создаёт gift_quotes, gift_requests, gift_attempts и gift_admin_decisions.
Пользователи, FSM, серия бонусов, настройки, спонсоры и промокоды не сбрасываются.

Перед изменениями рабочий бот остановлен. Защищённая консистентная копия создана
через SQLite backup API и зашифрована Fernet: `data/backups/stage7-20261003/`.
Расшифровка сверена с исходным снимком. Ключ хранится отдельно в локальном .env.
На отдельной расшифрованной копии в изолированном /tmp проверены
0013 → 0015 → 0013 → 0015, все исходные значения 24 таблиц, 8 финансовых полей,
одна начальная операция, сумма разниц округления 0.0000, integrity=ok, FK=0.
Проверка копии не открывала рабочую БД на запись.

## Заявки и восстановление

Подтверждение действительно две минуты. Серверный пользователь определяет
получателя; callback и FSM не содержат подменяемого recipient. Username
разрешается через MTProto, затем числовой ID проверяется. Без username нужен
доступный аккаунту настоящий InputPeer: карточка предлагает написать отправителю
либо установить username. Фиктивный access_hash запрещён.

Одна короткая BEGIN IMMEDIATE транзакция создаёт уникальную заявку по nonce,
проверяет гейты, ban/shadow-ban, долг, средства, подтверждённых друзей, дневной
лимит МСК, резервирует средства и записывает операцию. Сетевые вызовы выполняются
после закрытия транзакций. Перед оплатой повторно проверяются допуск, настройки,
бюджет, цена и фактические Stars отправителя.

| Состояние | Резерв и дальнейшее действие |
|---|---|
| pending | Резерв сохранён, возможны claim и отмена |
| waiting_funds | Резерв сохранён, ожидание Stars, аккаунта или бюджета; возможна отмена |
| processing | Один воркер и lease, отмена запрещена |
| succeeded | Резерв потреблён один раз; подтверждение telegram либо manual |
| failed | Только доказанная неудача, резерв возвращён один раз |
| cancelled | Отмена до claim, резерв возвращён один раз |
| reconciliation_required | Исход неизвестен; резерв сохранён, повторная покупка и автоматический возврат запрещены |

Lease до payment_started восстанавливает безопасную очередь. Lease после
payment_started переводит заявку на сверку. Прямой поздний PaymentResult
сохраняется на исходной попытке и может завершить удержанный резерв при совпадении
form/gift/recipient/sender/price. Конфликт с ручным решением отдельно оповещает
владельца. Сверка по одной цене, времени, получателю или изменению баланса не
является доказательством оплаты конкретной заявки.

У payments.sendStarsForm нет random_id; в starsTransaction нет form_id.
Exactly-once внешней оплаты не заявляется. request_retries, автоматический
FloodWait sleep и replay при reconnect отключены. Неизвестный исход закрывает
транспорт; это не отменяет подарок, уже принятый Telegram. FloodWait хранится
в БД и останавливает всю очередь аккаунта, в том числе после рестарта/отмены.
Безопасные временные ошибки чтения ограничены gifts.max_attempts.
Недостаток Stars или отсутствие сессии сохраняет очередь до устранения причины.

Дневной бюджет учитывает неподтверждённые оплаты консервативно, в том числе
после смены суток. Время подтверждённой оплаты отдельно от updated_at: просмотр,
уведомление и правка метаданных не изменяют дату расхода. Локальный учёт не
гарантирует неизменность настоящего баланса при тратах владельца вне бота.

Уведомления заявок отправляются после commit, максимум одна попытка на статус.
Ошибка уведомления записывается, но не отменяет результат и не повторяет оплату.
Владелец видит очередь, ожидание, сверку, попытки, журнал средств, бюджет,
аккаунт и источник подтверждения. Ручное решение требует основания, отдельного
подтверждения, owner-only проверки в сервисе и аудита. Retry неизвестного
результата запрещён. Изменять настройки настоящих расходов gifts.* может
только владелец.

## Запуск и откат

gifts.enabled=false и gifts.daily_budget_stars=0 по умолчанию: оплата выключена
до входа и назначения бюджета владельцем. Существующие withdraw settings
сохранены: минимум 15 единиц, 5 подтверждённых друзей, 5 заявок за сутки МСК.
Не запускайте второй polling. Вход выполняйте при остановленном боте:

```powershell
docker compose stop bot
docker compose run --rm bot python -m userbot.login
docker compose up -d bot
```

После входа отдельно проверить авторизацию, sender ID, чтение актуального
каталога и баланса; затем назначить бюджет и включить gifts.enabled.
Платный приёмочный сценарий требует отдельной команды владельца: точный
tg_id получателя, один обычный доступный подарок, максимальная цена и общий
предел расходов. Создать одну заявку, проверить один reserve и consume,
Telegram подтверждение и фактическое получение; повтор callback должен вернуть
ту же заявку. Без такой команды Stars не расходуются ради проверки.

Downgrade 0015 запрещён при наличии любой реальной истории заявок; 0014 запрещён
после финансовых операций либо при активных/изменённых резервах. После начала
работы не откатывайте БД слепо к старому снимку: сначала остановите воркер,
сверьте все неизвестные оплаты и сохраните новое защищённое состояние. Возврат
старой БД без учёта отправленных подарков может привести к повторной выдаче.


Аккаунт отправителя может отличаться от Telegram-аккаунта администратора бота.
OWNER_ID определяет права владельца в боте; USERBOT_PHONE и USERBOT_ACCOUNT_ID
проверяют выбранный личный аккаунт отправителя. Первый интерактивный вход
проверяет номер через getMe; затем фактический sender ID закрепляется локально.
