## Этапная разработка

Разработка идёт **строго по этапам** из `docs/SPEC.md`. Переход к следующему этапу — **только** по фразам: «следующий этап» / «дальше» / «норм, продолжаем». Слово «продолжай» = продолжай текущее, **не новый этап**.

В начале каждого нового этапа — план из 3-5 пунктов, потом ждать «ок».

## UI/UX (жёсткое правило)

- **Только inline-кнопки.** Никаких ReplyKeyboardMarkup.
- **Никаких slash-команд** для пользователя. Команды только: `/start` (entry-point Telegram) и `/admin` (вход в админ-панель).
- **Премиум-оформление:** заголовки с эмодзи, разделители `━━━━━━━━━━━━━━━`, метки `Шаг N из M`, точечные эмодзи (1-2 на сообщение), без «Привет, дорогой друг!».
- Тексты — в `locales/ru.py`, не хардкодом в хендлерах.
- Готовые UI-виджеты — в `utils/ui.py` и `bot/keyboards/`.

Пользователь явно сказал: визуал должен быть **максимально красивым и приятным**. Текущая реализация — это базовая планка, новый чат должен поднять её ещё выше.

## Архитектура

```
handlers (тонкие) → services (бизнес-логика) → repositories (БД) → SQLAlchemy
                  ↘ middlewares: db session, user upsert, ban check
```

- Async везде. Никаких блокирующих вызовов.
- Числа экономики — в таблице `settings` (key-value), не хардкодом.
- Soft-delete (is_deleted) для юзеров и важных сущностей. Не DELETE.
- Idempotency для критичных операций (выводы).
- Шифрование Telethon-сессий через Fernet.
- Type hints везде.
- `callback_data` формат: `{section}:{action}[:{id}]`, например `adm:sp:open:5`.

## Тестирование — только через Docker

Хост — Windows c Python 3.14, на нём НЕТ wheels для `orjson` / `aiohttp` / `Pillow` / `pydantic-core` — **не пытайся создавать локальный venv**. Реальный таргет — `python:3.12-slim` в Docker.

```
docker compose build           # пересборка (кэш слоёв спасает)
docker compose run --rm bot alembic upgrade head   # миграции
docker compose up -d
docker compose logs -f bot
curl http://localhost:8080/health
```

Реальный бот: `@TestBotSirius_bot`.

### 🔴 Авто-тест после КАЖДОГО изменения кода (обязательно, не опционально)

Как только написал/поправил код — **сразу, до ответа пользователю**:

1. `docker compose build` (исходники запекаются слоем `COPY . .`; без пересборки контейнер не увидит правки).
2. Прогнать весь pytest-suite в Docker:
   ```
   docker compose run --rm --no-deps bot sh -c "pip install -q pytest==8.3.4 pytest-asyncio==0.24.0 && python -m pytest -q"
   ```
   (pytest НЕ в prod-образе — ставится в рантайме одноразового контейнера. Детали — в HANDOFF §«🧪 Тесты».)
3. Если красное — **чинить до зелёного**, не оставлять падающих тестов и не отдавать работу пользователю.
4. **Покрывать новый код тестами**: добавил сервис/воркер/репо-метод — добавь тест в `tests/`. Менял поведение — обнови тест.
5. Менял миграции/схему — `docker compose run --rm bot alembic upgrade head` перед тестами.

Цель: пользователь получает только проверенный, зелёный код. Тесты — часть Definition of Done, а не отдельная просьба.
